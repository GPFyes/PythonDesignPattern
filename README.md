## 设计模式背景
**GoF**（Gang of Four，四人帮）是指 Erich Gamma、Richard Helm、Ralph Johnson 和 John Vlissides 四位软件工程专家。他们于1994年出版了《Design Patterns: Elements of Reusable Object-Oriented Software》一书，首次系统性地总结了23种面向对象设计模式。

---

## 设计模式核心思想

- **封装变化**：找出程序中变化的部分，将其与不变的部分分离
- **面向接口编程**：针对抽象类型编程，而不是针对具体实现
- **组合优于继承**：优先使用对象组合来实现复用

---

## 设计模式原则（SOLID）

 SOLID 是面向对象设计的五个基本原则，这些原则是 GoF 设计模式的基础。

### 1. 单一职责原则（SRP）

**定义**：一个类应该只有一个引起它变化的原因。也就是说，每个类只负责一个功能领域。

**核心思想**：将不同的职责分离到不同的类中，每个类只有一个关注点。

**违反后果**：
- 类变得臃肿，难以维护
- 一个职责的变化可能影响其他不相关职责
- 难以测试和复用

**如何遵循**：
- 识别类中的多个职责
- 将每个职责分离到独立的类
- 保持类的小而专注

---

### 2. 开闭原则（OCP）

**定义**：软件实体（类、模块、函数等）应该对扩展开放，对修改关闭。

**核心思想**：通过继承、接口、多态等机制，使系统能够在不修改现有代码的情况下扩展新功能。

**违反后果**：
- 修改现有代码可能引入新的 bug
- 难以测试已存在的功能
- 代码维护成本增加

**如何遵循**：
- 使用抽象（抽象类、接口）定义稳定的行为
- 通过子类扩展而非修改父类
- 使用策略模式、模板方法模式等

---

### 3. 里氏替换原则（LSP）

**定义**：子类型必须能够替换其基类型而不改变程序的正确性。

**核心思想**：子类是父类的更具体实现，所以子类对象可以出现在任何父类对象出现的地方。

**违反后果**：
- 运行时出现意外错误
- 破坏多态性
- 代码逻辑错误

**如何遵循**：
- 子类必须保持父类的行为 contract
- 子类不应该强化前置条件
- 子类不应该弱化后置条件
- 子类必须保持父类的不变性

---

### 4. 接口隔离原则（ISP）

**定义**：使用多个专门的接口比使用单一的总接口更好。一个类不应该被迫依赖于它不需要的方法。

**核心思想**：将大接口拆分为小接口，客户端只需要知道需要的方法。

**违反后果**：
- 肥接口：包含过多方法的接口
- 强迫实现不需要的方法
- 类之间产生不必要的依赖

**如何遵循**：
- 识别客户端的不同需求
- 创建小而专注的接口
- 类实现多个小接口而非一个大接口

---

### 5. 依赖倒置原则（DIP）

**定义**：高层模块不应该依赖于低层模块，两者都应该依赖于抽象。抽象不应该依赖于细节，细节应该依赖于抽象。

**核心思想**：面向接口编程，而不是面向实现编程。通过依赖抽象（接口、抽象类）来实现解耦。

**违反后果**：
- 高层模块依赖低层模块，耦合度高
- 难以替换低层实现
- 难以测试

**如何遵循**：
- 使用接口或抽象类定义依赖
- 高层模块定义接口，低层模块实现
- 使用依赖注入

---

### 6. 迪米特法则（LoD）

**定义**：一个对象应当对其他对象有尽可能少的了解。每个对象应该只与直接的朋友通信。

**核心思想**：减少对象之间的交互，降低耦合度。只与直接的朋友（当前对象本身、被当作参数传入的对象、方法返回的对象）交互。

**违反后果**：
- 过度耦合
- 难以理解和维护
- 修改一个对象可能影响多个其他对象

**如何遵循**：
- 只与直接朋友通信
- 不要和陌生人说话（避免链式调用）
- 封装内部细节

---

### 7. 合成复用原则（CRP）

**定义**：优先使用对象组合/聚合，而不是通过继承来达到复用的目的。

**核心思想**：组合是一种"has-a"（has-a）关系，继承是"is-a"（is-a）关系。优先使用组合可以在运行时动态改变行为。

**继承 vs 组合**：
- **继承**：静态的编译时绑定，无法在运行时改变
- **组合**：动态的运行时绑定，更加灵活

**违反后果**：
- 类层次结构过于复杂
- 难以理解对象行为
- 父类变化影响所有子类

**如何遵循**：
- 优先使用组合/聚合
- 仅在确实存在 "is-a" 关系时使用继承
- 使用接口实现多态

## 接口与设计模式

### 接口在设计模式中的作用

接口是设计模式的核心组成部分，主要作用包括：

1. **定义抽象层**：通过接口定义行为规范，将"做什么"与"怎么做"分离
2. **解耦实现**：客户端依赖接口而非具体实现，便于替换和扩展
3. **实现多态**：同一接口可以有多种实现，运行时动态选择
4. **约束行为**：确保实现类提供特定的方法和能力

### 接口与设计模式的关系

| 接口类型 | 相关设计模式 | 说明 |
|---------|-------------|------|
| **产品接口** | 工厂方法、抽象工厂 | 定义产品对象的统一接口 |
| **策略接口** | 策略模式、状态模式 | 封装可互换的算法 |
| **迭代器接口** | 迭代器模式 | 统一遍历不同集合的方式 |
| **命令接口** | 命令模式 | 封装请求为对象 |
| **观察者接口** | 观察者模式 | 定义通知机制 |
| **组件接口** | 组合模式、装饰器模式 | 统一组件行为 |
| **访问者接口** | 访问者模式 | 定义对元素的操作 |
| **中介者接口** | 中介者模式 | 定义对象间通信 |
| **适配器接口** | 适配器模式 | 统一不同接口 |
| **代理接口** | 代理模式 | 控制对对象的访问 |

### Python 中接口的实现方式

Python 使用多种方式实现接口概念：

#### 1. 抽象基类（ABC）

```python
from abc import ABC, abstractmethod

class Drawable(ABC):
    @abstractmethod
    def draw(self):
        pass

class Circle(Drawable):
    def draw(self):
        print("绘制圆形")

class Rectangle(Drawable):
    def draw(self):
        print("绘制矩形")
```

#### 2. Protocol（结构子类型）

```python
from typing import Protocol

class Drawable(Protocol):
    def draw(self) -> None:
        ...

# 无需显式继承，结构兼容即可
class Circle:
    def draw(self):
        print("绘制圆形")
```

#### 3. Duck Typing

```python
# 只需对象具有 draw 方法即可
def draw_shape(shape):
    shape.draw()  # 不需要显式接口声明
```

### 设计模式中接口的使用示例

```python
# 策略模式：策略接口
class PaymentStrategy(ABC):
    @abstractmethod
    def pay(self, amount):
        pass

# 状态模式：状态接口
class State(ABC):
    @abstractmethod
    def handle(self, context):
        pass

# 命令模式：命令接口
class Command(ABC):
    @abstractmethod
    def execute(self):
        pass

# 观察者模式：观察者接口
class Observer(ABC):
    @abstractmethod
    def update(self, data):
        pass

# 迭代器模式：迭代器接口
class Iterator(ABC):
    @abstractmethod
    def __next__(self):
        pass
    
    @abstractmethod
    def __iter__(self):
        pass
```

### 接口设计的最佳实践

1. **保持接口小而专注**：遵循接口隔离原则
2. **使用抽象类而非具体类**：依赖抽象而非具体
3. **避免肥接口**：将大接口拆分为小接口
4. **为接口命名要描述行为**：使用动词或形容词
5. **考虑未来扩展**：接口应具有通用性
